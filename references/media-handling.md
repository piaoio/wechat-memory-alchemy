# 媒介处理：八种形态，八条路径

一句话原则：**二进制不必入库，语义必须入库。**

资料库存不下大量原文件，也没必要。真正有价值的是"这张图里写了什么""这段语音说了什么"。

---

## 处理矩阵

| 媒介 | 到达形态 | 主路径 | 工具 | 产出字段 | 常见坑 |
|---|---|---|---|---|---|
| 文本 | 文本行 | 直接解析 | `build_records.py` | `content_raw` | 多行被当成多条 |
| 图片/截图 | `[图片]` + 文件 | 读文字 + 描述场景 | `ViewImage` | `media_desc` `content_raw` | 长图字太小 |
| 语音 | `[语音]` / 音频文件 | 转文字 | 微信「转文字」/ `AudioTranscribe` | `content_raw` | 方言识别差 |
| 视频 | `[视频]` + 文件 | 封面 + 标题 + 时长 | 取首帧看图 | `media_desc` | 体积大，别入库 |
| 文件 | `[文件]` + PDF/docx | 抽取正文 | office / pdf 技能 | `content_raw` | 扫描件是图 |
| 链接卡片 | URL | 抓正文 | `WebFetch` | `content_raw` | 公众号防爬 |
| 表情/贴纸 | `[表情]` | 记标签 + 情绪 | — | `emoji_tags` | 别丢，它是语气 |
| 小程序/转账 | `[小程序]` `[转账]` | 记元数据 | — | `msg_type` | 金额敏感 |

---

## 1. 文本

`build_records.py` 已处理：以「发送人行 + 时间行」为分隔，中间多行合并为**一条**消息。

要检查的边界情况：
- 一条消息里含空行 → 仍是同一条（已处理）
- 发送人昵称本身带换行 → 极罕见，会导致误切；发现后手工修正
- 系统消息（"XX 撤回了一条消息"）→ 无发送人，丢弃或标 `sender: 系统`

---

## 2. 图片 / 截图

**先问：这是"信息图"还是"生活照"？**

| 是信息图（截图、聊天记录截图、PPT、书页） | 是生活照 |
|---|---|
| 目标是**把字读出来** | 目标是**记住场景** |
| 用 `ViewImage` 提示"逐字转录图中文字，保留排版层级" | 用 `ViewImage` 提示"描述画面内容、地点线索、出现的物件与人数" |
| `content_raw` = 转录文字 | `content_raw` = `[图片]`，`media_desc` = 描述 |

长截图（消息记录长图）额外要求：
1. 先看整体判断有几段
2. 字太小/被压缩时，说明"请提供分段截图"而不是硬猜
3. 转录后**保留原有的发送人分段**，方便还原因果

**绝不做的**：看图编故事。看不清就写"图中文字模糊，无法辨认"，标 `confidence: low`。

---

## 3. 语音

微信语音有两条路：

**A. 用户在微信内转文字**（推荐）
微信长按语音 →「转文字」→ 复制 → 转发文字过来。
优点：微信自己的模型对口语和方言更熟。缺点：用户多一步操作。

**B. 音频文件 + `AudioTranscribe`**
适用于用户能导出音频的场景。支持中英文与方言，可区分说话人。

无论哪条路，转写文本都要：
- 保留语气词（"嗯""那个"）——这是判断情绪的关键
- 标 `confidence: low` 如果出现明显不合理（专有名词全错、语句断裂）
- 记时长：`[语音 12"]`，长语音往往比短语音更重要

---

## 4. 视频

不入库原文件（体积）。只取三样：

1. **时长**
2. **封面/首帧**（`ViewImage` 描述画面）
3. **上下文说明**（用户为什么发这个）

`media_desc` 写成一句话："一段约 30 秒的街景视频，画面是雨夜的路口"。

---

## 5. 文件（PDF / Word / Excel / PPT）

先加载 `workbuddy-office-routing`，按类型走对应技能抽正文。

| 类型 | 抽取重点 |
|---|---|
| PDF | 正文 + 页数；扫描件先判断是否需 OCR |
| Word | 正文 + 标题层级 |
| Excel | 表头 + 前 20 行 + 行列数（不要全文塞进记录） |
| PPT | 逐页标题 + 关键要点 |

表格数据不要塞进聊天记录表，单独建表或用 `records.csv` 之外的 `tables/` 存放。

---

## 6. 链接与公众号文章

主路径：`WebFetch` 抓正文，提示词要指定抽什么：

```
抽取这篇文章的：标题、作者、发布时间、正文全文、3-5 个核心论点。
如果页面需要登录或内容为空，直接说明"无法获取正文"，不要编造。
```

降级链（必须逐级降，不许跳）：

```
正文 → 标题+首段+链接 → 标题+链接+用户口述一句话
                                    （标 confidence: low）
```

公众号特有问题：
- 部分文章有防爬 / 需在微信内打开 → 走降级
- 图片型文章（长图排版）→ 抓到的正文是空的，改为"建议截图"
- 抓到的正文常带"点击上方蓝字关注"等噪声 → 清洗掉，但**不要改动正文本身**

---

## 7. 表情与贴纸

`[送心]` `[捂脸]` `[裂开]` 这些不是噪声，是**语气标记**。处理：

- `emoji_tags` 字段保留原标签
- 情绪判断时给权重（`[裂开]` → 无奈/崩溃）
- 不要翻译成"微笑"这类书面词，原样保留

自定义表情包（非 emoji）记为 `[表情包]`，若含文字则转录文字。

---

## 8. 小程序 / 转账 / 位置 / 名片

只记元数据，不解析内容：

| 类型 | 记录内容 |
|---|---|
| 小程序 | 小程序名 + 分享标题 |
| 转账/红包 | `[转账]` + 金额（**标 privacy: sensitive**） |
| 位置 | 地名（保留，是重要场景线索） |
| 名片 | 被推荐人昵称 |
| 接龙 | 完整接龙文本（这是结构化数据，值得全文保留） |

---

## 混合内容的拆解

一条消息常常混多种媒介：

```
[图片]
这是刚才拍的合同
金额改成 12 万了
```

处理顺序：**先拆媒介，再归并语义**。
1. 图片 → 转录（合同关键条款）
2. 文本 → 保留
3. 合并为一条记录，`msg_type: mixed`，`media_desc` 写图片内容，`content_raw` 保留原文与转录

不要拆成三条记录——它们在一次发言里，语义上是一个整体。
